00 · Ground truth

What the code does today

Eight things worth knowing before any of this gets built. Four are live bugs the new features would inherit and amplify, so they get fixed first regardless of where you start. The recent auth hardening — secure cookie prefixes, an exp on the WebSocket access token, no more token logging — is good and stays.

Bug

The broadcast endpoint has no authentication.

POST /broadcast on the WebSocket server accepts any JSON from anyone who can reach the port and fans it out to every connected admin. The upgrade handshake verifies a JWT; the HTTP hook next to it verifies nothing. Bind it to loopback, or require a shared secret header — before it starts carrying order alerts.

Bug

Checkout ignores the unit a customer bought in.

CartItem.unit can be 'kg', but checkout validates against product.quantity (pieces), prices with product.price (per piece), and reserves from the piece pool. Order 2 kg of seer and you reserve two fish and get charged twice the piece price. Moving to kilos removes the ambiguity rather than patching it.

Bug

The checkout "transaction" is a no-op.

mongoose-mock.ts exports a MockSession whose startTransaction and commitTransaction do nothing. Checkout creates the order, then reserves stock, and believes a throw will roll both back. Nothing rolls back. An oversell leaves a pending order and a reservation that never releases.

Bug

Two stock pools for one physical fish.

quantity (pieces) and stockKg move independently. Selling a piece never reduces the kilos; selling kilos never reduces the pieces. The same pomfret can be sold twice, once each way, and both numbers still look healthy.

R1 · Fresh stock

Kilos, one day, and a book for tomorrow

Four decisions collapse most of the complexity. Everything is priced and counted in kilograms. A catch is sellable for exactly one business day — no carry-over, no Day 2, no discounting yesterday's fish. Orders placed after 19:30 are drawn from tomorrow's catch. And because of that, stock stops being one number on a product and becomes one row per product per day.

One unit: kilograms

Fish is sold by weight in India, so the app should be too. quantity, stockKg, price, pricePerKg and CartItem.unit collapse into kilos of stock at a price per kilo. The dual-pool bug disappears because there is only one pool, and the admin types one number per fish instead of two.

  • Order quantities in 250 g steps, with a per-product minOrderKg and maxOrderKg so one customer can't book the whole catch.
  • For items people picture as whole animals — crab, lobster, a single pomfret — keep an optional avgPieceWeight and show "≈ 1 fish, about 600 g" as a helper under the kg selector. The transaction stays in kilos; only the explanation is in pieces.

The shape of a day

The bug your 19:30 answer exposed. Rev 2 decided today-vs-tomorrow by comparing the wall-clock hour to the cutoff. That is wrong for every minute between midnight and 04:00: the business day has already rolled back to yesterday, but the clock reads 01:00, which is less than 19:30 — so an order at 1 a.m. would be sold yesterday's catch, which no longer exists.

The fix is to stop using the wall clock and measure minutes elapsed since the day started. 19:30 is 930 minutes into a day that begins at 04:00; anything at or past 930 belongs to tomorrow. Verified across the clock:

// src/lib/business-day.ts — every time question answered in one place
export const DAY_START_MIN = 4 * 60;          // 04:00 IST
export const CUTOFF_MIN    = 19 * 60 + 30;   // 19:30 IST wall clock
export const CUTOFF_ELAPSED = (CUTOFF_MIN - DAY_START_MIN + 1440) % 1440; // 930
const IST_OFFSET_MIN = 330;

function istMinutes(d: Date) {
  const ist = new Date(d.getTime() + IST_OFFSET_MIN * 60_000);
  return ist.getUTCHours() * 60 + ist.getUTCMinutes();
}

/** "2026-09-13" — the fish day `d` belongs to. */
export function businessDay(d: Date = new Date()): string {
  const ist = new Date(d.getTime() + IST_OFFSET_MIN * 60_000);
  ist.setUTCMinutes(ist.getUTCMinutes() - DAY_START_MIN);
  return ist.toISOString().slice(0, 10);
}

/** Minutes elapsed since this business day began. 0 … 1439. */
export function elapsed(d: Date = new Date()) {
  return (istMinutes(d) - DAY_START_MIN + 1440) % 1440;
}

/** Which day's catch fills an order placed now. Never trust the client. */
export function fulfilDay(d: Date = new Date()): string {
  const today = businessDay(d);
  return elapsed(d) < CUTOFF_ELAPSED ? today : addDays(today, 1);
}

Stock is per day, not per product

This is the structural consequence of next-day fulfilment. An order placed at 22:00 must not touch today's fish — it holds a claim on a catch that hasn't landed yet. One number on Product cannot express that. 

model DayStock {
  id          String    @id @default(cuid())
  productId   String
  day         String    @db.Char(10)   // the catch day this row is for

  planned     Float     @default(0)    // kg expected — the pre-order cap
  declared    Float     @default(0)    // kg that actually landed — the truth
  reserved    Float     @default(0)    // kg held by live orders for this day
  sold        Float     @default(0)    // kg handed over — can never be undone
  declaredAt  DateTime?                // null = not declared yet; also orders the rail
  pricePerKg  Float                    // price is per catch, not per product

  @@unique([productId, day])
  @@index([day])
}

Note pricePerKg living here rather than on Product: fish price moves with the catch, and pinning it to the day means an order's price is provably the one that was displayed, and yesterday's price never leaks into today.

RowSold againstStorefrontFresh rail
Today, declaredAt set declared − reserved Buyable · "Landed today" Yes, newest declaration first
Today, not yet declared nothing "Landing now — back by 6 AM" No
Tomorrow, planned > 0 planned − reserved Pre-order · "Delivered tomorrow" No
Any earlier day nothing, ever Gone at 04:00 No

The one consequence of dropping Day 2: between 04:00 and the morning declaration, today has nothing to sell. That is correct rather than broken — you have no fish yet — but it must be designed, not discovered. The storefront shows a "landing now" state and keeps tomorrow's pre-orders open, so the shop is never a dead end; and the admin gets a push at 05:00 if today is still undeclared. Traffic in that window is near zero anyway.

Declare, don't increment

A stock entry is a declaration of what is physically on ice right now, not a delta. Typing 12 means there are twelve kilos. It never means "add twelve".

  • Saving twice is harmless. Retrying on a dropped connection is harmless.
  • A mid-day top-up is the same gesture as the morning entry — re-declare the new total.
  • The AI agent's increment bug disappears by construction.
  • Invariant: declared ≥ sold. You cannot un-sell fish. declared may fall below reserved — that is precisely what raises a short-fall, covered next.

Every declaration writes a StockLog row (productId, day, field, before, after, source, actorId): fifteen lines that answer "who zeroed the pomfret" and "how much did we not sell last week".

Reserving stock without the race

Read-then-increment can oversell under concurrency, and the fake transaction means a failure halfway leaves debris. Both are fixed by putting the guard in the WHERE clause inside a real transaction. Which column guards depends on whether the order is for today or tomorrow — decided server-side, never from the client. 

const day = fulfilDay();
const col = day === businessDay() ? 'declared' : 'planned';

await prisma.$transaction(async (tx) => {
  for (const line of lines) {
    const rows = await tx.$executeRawUnsafe(
      `UPDATE DayStock SET reserved = reserved + ?
         WHERE productId = ? AND day = ? AND (${col} - reserved) >= ?`,
      line.kg, line.productId, day, line.kg,
    );
    if (rows === 0) throw new OutOfStock(line.name, day);
  }
  await tx.order.create({ data: { ...order, fulfilDay: day } });
});

Only col is interpolated and it comes from a two-value branch — never from request data. This also gives a useful property for free: when a short catch leaves declared < reserved, the guard goes negative and new sales of that fish stop automatically until the short-fall is resolved. Nobody has to remember to close it.

Delete mongoose-mock.ts along the way. A shim that silently pretends to be transactional is worse than no transaction, because the calling code is written as if it were safe.

R2 · The hard case

When the boat comes back light

You asked me to work this one out rather than decide it cold, so here is the whole chain of reasoning. The situation: customers pre-ordered 6 kg of vanjaram for today, their money is already taken through Razorpay, and 4 kg landed. Someone owes someone fish or money, and it is 5 a.m.

Four things that are true before any rule is chosen

  • The money moved first. Razorpay collects upfront, so a short catch is always a refund question, never a "we'll charge you less" question.
  • An unresolved short-fall is the worst outcome. Money taken, no fish, no word. Worse than any refund policy. So the resolution cannot depend on the admin being awake and attentive.
  • Only the customer can accept a substitute. You cannot decide that barracuda replaces seer on their behalf.
  • Partial fish is sometimes fine and sometimes insulting. 3 kg of a 5 kg order is a reasonable outcome. 1.2 kg of a 5 kg order is not — that customer was cooking for a crowd.

The rules that follow

Rule 1

Fill in the order people paid, oldest first.

FIFO by paidAt. It is the only allocation anyone finds fair without explanation, and it is the only one that can't be gamed by order size. Pro-rata was the alternative and it is worse: it converts one disappointed customer into five partly-disappointed ones and five partial refunds.

Rule 2

Part-fill only if it covers at least half the order, and at least minOrderKg.

Otherwise refund that order in full and pass the fish down the queue. This is the rule that stops a 5 kg order from swallowing a 1.2 kg catch and leaving the 1 kg order behind it with nothing — see case E below. Strict FIFO without it produces two unhappy customers where one clean refund and one full delivery was available.

Rule 3

Allocate against declared − sold, not declared.

Fish already handed over is gone. Re-running allocation after a mid-day re-declaration must never try to claw back a delivered order.

Rule 4

The customer chooses, but a clock guarantees the money moves.

On short-fall, push immediately: "Vanjaram came up short. Take 3 kg instead of 5 (₹2,400 back), swap for sankara, or cancel for a full refund. If we don't hear from you by 08:00 we'll refund automatically." A scheduled job refunds everything unanswered at the deadline. The admin never has to clear a queue for the money to be right.

Rule 5

A substitute is offered at the original line total or less — never more.

If the swap is cheaper, refund the difference. If it's dearer, the shop absorbs it or doesn't offer it. Charging a second time for a substitute means a fresh Razorpay payment on a fish the customer never asked for, which is both a bad experience and a refund dispute waiting to happen.

Rule 6

Every refund is idempotent and logged.

Unique key on (orderItemId, reason) plus Razorpay's own idempotency, so the auto-refund job running twice — or a webhook retry — cannot pay twice. Store OrderItem.fulfilledKg and refundedAmount; add 'Partial' to the existing refundStatus values.

The allocation, in full

function allocate(declared: number, sold: number, orders: Line[], minOrderKg: number) {
  let rem = declared - sold;                // Rule 3
  for (const o of orders) {              // Rule 1 — sorted by paidAt asc
    const need = Math.max(minOrderKg, 0.5 * o.kg);   // Rule 2
    const give = Math.min(o.kg, rem);

    if (give >= o.kg)       { o.state = 'FULL';    o.filled = o.kg; }
    else if (give >= need)  { o.state = 'PARTIAL'; o.filled = give; }
    else                   { o.state = 'SHORT';   o.filled = 0;    }

    rem -= o.filled;
  }
  return { orders, leftover: rem };   // leftover goes on general sale today
}

Run over thirty thousand randomised mornings, this holds three invariants with no violations: never allocate more than landed, never mark PARTIAL below the threshold, never allocate anything to a SHORT order. The five cases worth understanding:

CaseLandedOrders (oldest first)OutcomeLeftover
A catch covers it 12.0 2.0 · 3.0 · 1.5 all FULL 5.5 on sale
B clean FIFO cut 4.0 2.0 · 2.0 · 2.0 FULL · FULL · refund 0
C stub remainder 4.3 2.0 · 2.0 · 2.0 FULL · FULL · refund — 0.3 kg is below half of 2.0 0.3 on sale
E big order would starve the queue 1.2 5.0 · 0.5 refund · FULL — Rule 2 passes the fish down 0.7 on sale
F half-fill is acceptable 3.0 5.0 · 1.0 PARTIAL 3.0, 40% refunded · refund 0

Case E is the one worth staring at. Strict FIFO gives the 5 kg order a 76% short delivery and the 0.5 kg order nothing — two unhappy customers. Rule 2 turns it into one clean refund, one perfect delivery, and 0.7 kg left to sell. The rule pays for itself in exactly this shape of morning.

Situations the rules have to survive

SituationWhat happens
More landed than planned Nothing special. planned caps pre-orders; it never caps the catch. Surplus goes on sale for today.
Admin re-declares lower at noon (miscount) Allocation re-runs against declared − sold. Only orders whose allocation dropped and that haven't been notified get a push — tracked by shortfallNotifiedAt per item, so no one is told twice.
Customer answers after the 08:00 deadline Refund already issued; the reply is shown as "already refunded" with a link to reorder. No double refund — Rule 6.
New orders arriving during an unresolved short-fall Blocked automatically: declared − reserved is negative, so the reservation guard fails. As refunds release reserved, capacity reopens on its own.
No catch at all — storm, boat didn't sail One "No catch today" button declares zero across every product and fires the whole short-fall flow at once. Without it the admin is zeroing 26 rows by hand in a panic.
Customer cancels before the catch lands Free and instant — nothing has been prepared. Releases reserved immediately.
Short-fall on one line of a multi-fish order Resolved per line. The rest of the order ships; only the short line is refunded or substituted. Order total recalculated from fulfilledKg.

What the admin actually has to do. Declare the catch. That's it. The allocation runs, the pushes go out, the refunds land at 08:00 whether or not anyone opens the dashboard. The short-fall panel exists so the admin can offer a substitute and see who was affected — not because the system needs them to.

R3 · Admin

One sheet, two columns, one save

Today, changing the stock of one fish means opening a dialog with sixteen fields — name, Tamil name, aliases, slug, description, two prices, image upload — and saving all of it. Twenty-six products is twenty-six dialogs. The daily job and the occasional job share one form, and the daily job loses.

So split them. Today's Stock at /admin/stock becomes the admin landing page and handles the only things that change daily: what landed, what's expected tomorrow, and the price. Everything else moves to Edit details, reached from a row and opened maybe once per product per year.

Ordering — the list sorts itself by what needs attention

  • Short-fall first — pre-orders today's catch can't cover. The refunds are already scheduled; this row is where a substitute can still be offered.
  • Not declared today next, in UNDECLARED — the morning's to-do list, shrinking as you work.
  • Done today last, FRESH — collapsed, out of the way.

Per row

  • Two numbers, both in kg: what landed today, what you expect tomorrow. The second is the entire pre-order mechanic, exposed as one extra field.
  • Tomorrow is pre-filled from a rolling median of that fish's recent declarations, so the job is confirming a number rather than inventing one. That is the difference between a column that gets maintained and one that goes stale.
  • inputMode="decimal" so phones open the number pad; 44px tap targets for wet hands.
  • Same as yesterday copies the last declaration. Nothing today zeroes in one tap. No catch today sits at the top and zeroes everything.
  • Price sits behind a chevron — it changes less often than stock, and hiding it halves the visual noise.

Save semantics

  • Edits stay local and mark the row dirty. Nothing hits the network per keystroke.
  • One sticky Save N changes bar — bottom on mobile, right-aligned on desktop.
  • One request, one transaction: POST /api/admin/stock-day with { day, rows: [{ productId, declared?, planned?, pricePerKg? }] }. Declarative, so a retry is safe.
  • The save response returns the allocation result, so the short-fall banner appears in the same round trip as the declaration that caused it.
  • Optimistic UI with rollback on failure, reusing the toast pattern already in ProductManager.
  • A 10-second Undo after save — cheaper than a confirm dialog, and it protects against the real error, a fat-fingered zero. Undo also rescinds an allocation, which is why the refund deadline is 08:00 and not immediate.
  • Unsaved edits persist to localStorage keyed by business day. Harbour signal drops; the morning's work shouldn't.

Mobile and desktop from one component

Don't build a card list and a table. Build one StockRow whose grid template changes at the breakpoint: stacked with big steppers under 640px, aligned columns above it. Same markup, same state, same code path — which is why the two will still agree six months from now. On desktop, Tab walks down the today column and Enter saves.

The AI agent becomes a draft, not a write

MultimodalInventoryAgent is a good idea sitting on the wrong side of the save. Right now it writes to the database directly, with non-idempotent increments and no review step.

Point it at the sheet instead: photograph the crates, say "vanjaram pathu kilo, vaval ettu", and the agent returns a draft that pre-fills those rows as dirty and highlighted. The admin glances, corrects, hits the same Save. The model gets to be fast and occasionally wrong, which is the only safe way to use it — and the declaration semantics make a double-tap harmless.

R5 · Identity

Three keys, one door, Firebase at the gate

You've built phone OTP on Firebase in a local directory — it isn't on main at 9812bcf, so what follows is the contract it needs to meet rather than a description of what you wrote. firebase and firebase-admin are already in package.json, so no new dependency. The shape that matters: Firebase proves the phone, NextAuth owns the session. Keeping those separate is what stops you ending up with two competing identity systems.

Identity fields

FieldRequiredUniqueRules
usernameYesYes 3–20 chars, a-z 0-9 . _, stored lowercase. Never all digits — that rule is what keeps a username from colliding with a phone number at login. Reserve admin, aquacart, support, api.
phoneYesYes Stored canonical as +91XXXXXXXXXX. Normalize on write, always — otherwise 98765 43210 and +919876543210 become two accounts and the duplicate check silently fails.
phoneVerifiedAtYes— Set only by the server after verifyIdToken succeeds. Replaces isEmailVerified as the gate on login.
emailNoWhen present MySQL permits many NULLs in a unique index, so optional-and-unique needs no special handling. Shape validation only — drop ALLOWED_EMAIL_DOMAINS.
passwordYes— bcrypt, unchanged. Drop every *VerificationToken / tempEmail* column.

Signup order of operations

  1. Check the duplicate before sending the SMS. POST /api/auth/availability with the normalized phone and username. If the number is already registered, stop — show "This number already has an AquaCart account", offer Log in with the number carried across, and never spend an OTP on a known duplicate. Your original requirement, and also the cheapest guard against SMS abuse.
  2. Client runs the Firebase flow. signInWithPhoneNumber → user types the code → confirmationResult.confirm() → a Firebase ID token.
  3. Server verifies the token, not a flag. getAuth().verifyIdToken(idToken), then assert all four: decoded.phone_number equals the submitted canonical phone, decoded.aud is your project, auth_time is within ten minutes, and the phone is still unclaimed.
  4. Create the user with phoneVerifiedAt = now(), then signOut() the Firebase client. The app session is NextAuth's.

Two things to check in what you've already built. First: if the client ever posts something like { verified: true } and the server trusts it, the whole flow is decorative — anyone can curl past it. Only a server-side verifyIdToken counts.

Second: SMS toll fraud is the standard attack on Firebase Phone Auth — scripted signups pumping OTPs until your quota is drained. Four settings close it: enable App Check (reCAPTCHA Enterprise on web), restrict allowed regions to India only, set a daily SMS cap, and rate-limit /api/auth/availability per IP. The region lock alone removes most of it.

Resolving what they typed at login

Verification is a signup and reset gate. Login itself stays password-based and accepts any of the three identifiers in one field. 

// src/lib/identifier.ts
export function classify(raw: string) {
  const s = raw.trim();
  if (s.includes('@')) return { kind: 'email', value: s.toLowerCase() };

  const digits = s.replace(/[\s()+-]/g, '');
  if (/^\d{10,13}$/.test(digits))
    return { kind: 'phone', value: '+91' + digits.slice(-10) };

  return { kind: 'username', value: s.toLowerCase() };
}

In the credentials provider, swap email for identifier, replace the isEmailVerified throw with phoneVerifiedAt, and run a dummy bcrypt compare when no user is found so response timing doesn't leak which accounts exist. Login stays quiet about existence; signup, by design, does not.

Password reset — solved by the same flow

Reuse the Firebase OTP: enter the phone, verify, set a new password. The server accepts the reset only if verifyIdToken succeeds and the token's phone_number matches an existing account. Keep one manual escape hatch — an admin-issued reset code, audit-logged — for the customer whose number has changed. That path needs the caller to state their last order before you issue anything.

Review checklist for the local branch

  • Server calls verifyIdToken; no client-supplied "verified" boolean is trusted anywhere.
  • decoded.phone_number is compared against the canonical submitted phone, not just presence-checked.
  • Duplicate check runs before the SMS is sent.
  • Phone is normalized to +91… on every write path, including the admin seed.
  • Firebase client is signed out after verification, so no stray Firebase session lingers.
  • App Check on, region restricted to IN, daily SMS cap set, availability endpoint rate-limited.
  • Authorized domains in the Firebase console include the Netlify domain and localhost.
  • Service-account JSON is a server-only env var — never NEXT_PUBLIC_.

What gets deleted

api/verify-email, api/verify-otp, api/resend-otp, (auth)/verify-email, VerifyEmailForm, sendVerificationEmail, and ALLOWED_EMAIL_DOMAINS. Order.customerEmail becomes nullable with customerPhone as the contact of record; the invoice mail only goes out when an address exists, and OrderManager's search should cover phone and username.

R6 · Notifications

Alerts for the shop, tracking for the customer, moments for both

Three audiences, two channels, and you already own most of the plumbing: a role-gated WebSocket server for the admin, and a Firebase project plus next-pwa for customers.

Admin — a new order lands

src/server/websocket.ts is already an admin-only WSS with a JWT-checked upgrade and a POST /broadcast hook. Fire it from the Razorpay webhook, not from checkout/verify — the webhook is the path that still arrives when the customer closes the tab mid-payment.

  • Authenticate /broadcast first (finding 1). Loopback-only binding, or a shared secret header. It currently accepts anything.
  • Reconnect with exponential backoff, and on reconnect refetch orders since the last seen id. A socket alone silently drops everything that happened while the laptop was asleep — the refetch is what makes it reliable.
  • Badge count plus a short sound, and a toast that deep-links to the order. One sound per order, never per message.
  • Second use for the same channel: the 05:00 "today is still undeclared" nudge, and the short-fall notice when an allocation comes up short.
  • The access token still travels in the ?token= query string, which proxies log. The new exp limits the damage; moving it to a Sec-WebSocket-Protocol header would close it.

Customer — order tracking

Use FCM web push — the same Firebase project you added for OTP, so no new vendor and no new billing relationship.

  • public/firebase-messaging-sw.js alongside the existing next-pwa service worker; VAPID key in env; getToken() only after an explicit in-app opt-in, never on first page load.
  • PushDevice { userId, token, platform, createdAt, lastSeenAt }. Prune on messaging/registration-token-not-registered — dead tokens accumulate fast.
  • Fire on ORDER_STATUS transitions: Confirmed → Out for delivery → Delivered, plus payment failure and short-fall. Idempotent on (orderId, status) so a webhook retry doesn't double-notify.
  • Deep-link into the order, not the home page.
  • iOS caveat: web push only works once the PWA is installed to the home screen (iOS 16.4+). Worth a one-line "Add to Home Screen" nudge rather than a silent failure.

Moment marketing — the declaration is the moment

This falls out of R1 for free. When the morning sheet saves and a product goes from nothing to declared kilos, that is a real event with a real deadline — exactly the thing worth a push, and the reason it won't read as spam.

வஞ்சிரம் just landed — 12 kg

₹1,200/kg · order before 7:30 PM for delivery today

  • Opt-in by intent. A Notify me when this lands button on any product that hasn't been declared today, plus per-category subscriptions. CatchAlert { userId, productId?, category? }. High intent, genuinely useful, and it doubles as demand data for tomorrow's planned figures.
  • Second moment worth having: a reorder nudge when something a customer bought before lands again, drawn from OrderItem history.
  • Guardrails matter more than the feature. One marketing push per user per day, quiet hours 21:00–06:00 IST, and marketing consent stored separately from transactional — muting offers must never mute "your order is out for delivery" or a short-fall notice.
  • Queue it, don't send inline. The sheet save must stay fast. Write NotificationJob rows in the same transaction as the declaration, and drain them from a scheduled function. Retries and a send log come free.

The cutoff turns every catch alert into a genuine deadline — "order before 7:30 PM" is true, not a growth tactic. That is the difference between a notification people keep on and one they turn off in week two.

07 · Explainer

Delivery slots, and whether you need them yet

You asked what this means. A delivery slot is a named time window a customer picks at checkout — say 07:00–10:00 or 17:00–20:00 — with a limit on how many orders each window can hold. Two separate ideas live inside it: telling the customer when, and capping how many.

Why it comes up here

Right now fulfilDay answers which catch, not when it arrives. "Delivered tomorrow morning" is a promise with no time attached. That's tolerable at low volume and stops being tolerable for three reasons:

  • Fresh fish needs someone home. It can't sit at a gate for four hours in Tamil Nadu heat. A window is the difference between a delivery and a wasted trip.
  • A 19:30 cutoff already implies more than one run. An order at 08:00 and an order at 19:00 cannot be on the same trip. You are effectively running a morning round and an evening round today — slots just make that visible instead of implicit.
  • Capacity is a real limit. One rider on one round can carry maybe 25 orders. Without a cap, the 40th order of the morning gets accepted and then disappoints — the same failure as overselling stock, in a different dimension.

What I'd do

Now

Two fixed runs, assigned automatically. No customer choice, no cap.

Add Order.slot as 'MORNING' | 'EVENING', derived from the same elapsed-minutes function that picks fulfilDay: ordered before ~11:00 → that day's evening run; after → next morning. One column, no new UI, and the customer finally sees "Arriving tomorrow, 7–10 AM" instead of a vague "tomorrow". This is worth doing in Phase 1 because it costs almost nothing and it makes every notification and invoice more concrete.

Later

Customer-chosen windows with a capacity guard.

A DeliverySlot { day, slot, capacity, booked } row, reserved at checkout with exactly the same conditional update that guards stock: WHERE booked < capacity. If it can't be reserved, the slot greys out in the picker. Build this when you start turning orders away or when two runs stop being enough — not before. It is the same pattern you'll already have written for DayStock, so it's a small addition when the day comes.

The thing to avoid is offering a choice of windows without a capacity cap. That reads as a promise and behaves as a guess, which is worse than not asking.

09 · Decisions

Still open

Everything structural is now decided. What's left are numbers you can change in one line, and one question I'd want answered before Phase 3.

  1. The 08:00 refund deadline. Long enough that a customer waking up can choose, short enough that money doesn't sit. If your morning round leaves earlier, this should move earlier with it.
  2. The half-order part-fill threshold. I picked 50% because it's the point where a partial delivery stops being useful. If your customers mostly order 1 kg, this rarely fires; if they order for functions, it will fire often and is worth tuning.
  3. Does the physical shop share this stock? If walk-in customers buy from the same ice, the app's declared is not the truth for long, and the admin needs a quick "sold 3 kg at the counter" adjustment — otherwise online customers get promised fish that already walked out the door. This is the one thing that could still surprise you.
  4. Delivery radius and charge — not modelled anywhere yet, and it interacts with slots when you get there.
